# Switchboard — project guide

A macOS Electron app — light or dark theme — that browses AI coding-agent conversations from both **Claude Code and Codex**: read-only transcript preview, resume/new into a real terminal (node-pty + xterm.js), a live "Formatted" view, and pinning. The layout is a single unified left rail (Pinned / Live / Recent conversations) beside the conversation area, which holds **tabs**, an optional **vertical split** into two panes, and any number of **windows** — all three behind one **feature flag** (`useTabsEnabled`, **default off**; the UI calls it Preferences → **Beta Features**, its own page between Application and Shortcuts), and all three governed by one rule: a conversation holds exactly ONE tab across the whole app, so opening it again reveals the tab it already has rather than making a second. See the **Tabs, panes and windows** section in [docs/architecture.md](docs/architecture.md). **All conversation data is derived from the session files each agent writes — Claude Code's JSONL under `~/.claude/projects/`, Codex's rollouts under `~/.codex/sessions/`** — Switchboard never owns it; Codex rollouts marked `thread_source:"subagent"` are intentionally omitted from the top-level conversation list. The one exception is **rename** — and even that writes through each agent's *own* store, never a Switchboard one: Claude Code gets the same `custom-title` line `/rename` writes (real, survives into `claude --resume`); Codex's rename calls the app-server `thread/name/set`, which Codex records to BOTH the volatile `state_*.sqlite` (`threads.title`, re-derived from the first message on resume) and the durable append-only `session_index.jsonl`; Switchboard resolves the displayed title the way Codex does — a *distinct* `threads.title`, else the `session_index.jsonl` name. See the **Multi-agent (Codex)** + **Conversation rename + info modal** pointers in [docs/architecture.md](docs/architecture.md).

Stack: Electron 42 (pinned as `latest`, so it tracks upstream) · electron-vite · React 18 + Vite · TypeScript (strict) · plain CSS · node-pty · chokidar · @xterm/xterm · react-markdown · KaTeX (lazy-loaded) · fuse.js. No Tailwind, no state library (plain hooks + localStorage).

## Set up Switchboard (first run)

When the user asks to **"Set up Switchboard"** (typically from a fresh clone — this is the phrase the public README's "Set up" section points them at), run the one-shot setup and then open the built app:

```bash
npm run setup
open dist/mac-arm64/Switchboard.app
```

`npm run setup` (= `scripts/setup.mjs`) installs dependencies, rebuilds `node-pty` for Electron's ABI, and packages `dist/mac-arm64/Switchboard.app` — but it does **not** launch the app, so always follow it with `open`. If it fails on a missing prerequisite (Xcode Command Line Tools, or Node 26 — see `.nvmrc`), walk the user through installing it, then re-run.

## Update Switchboard

When the user asks to **"Update Switchboard"** (the phrase the public README's "Updates" section points them at), pull the latest and re-run the one-shot build, then reopen:

```bash
git pull
npm run setup
open dist/mac-arm64/Switchboard.app
```

`npm run setup` rebuilds `dist/mac-arm64/Switchboard.app` from the pulled source (deps + `node-pty` + package). Tell the user to **quit (⌘Q) any running instance first** — `open` only focuses an already-running app, so a stale instance won't pick up the new build otherwise. If `git pull` reports local changes/conflicts or the build fails on a prerequisite, surface that rather than forcing past it.

## Build, validate, run

Full first-run setup, the dev loop, and the contributor quality gates live in README → **Develop**; this section is the **validate-before-done** checklist. The building blocks (run individually as needed):
1. `npm run typecheck` — `tsc` over BOTH projects (main = node, renderer = web). Must be clean.
2. `npm run build` — `electron-vite build` → `out/`. Must succeed. **Does NOT update the `.app`** — `out/` is what the **boot smoke check** consumes (so run `build` first); `npm run dev` runs its own build, and the packaged `.app` is separate.
3. **Boot smoke:** `SWITCHBOARD_SMOKE=1 node_modules/.bin/electron .` — prints `SMOKE PASS | pty:true | window:loaded`. The only headless check that node-pty loads/spawns under Electron's ABI and the renderer loads. `window:none` is a sampling race (re-run); only `did-fail-load` / `preload-error` lines indicate a real failure.
4. `npm test` — vitest over `test/` (55 suites: main-side parser/indexer/rename/customTitle/windowState/windowFocus/codexParser/codexThreadsDb/codexSessionIndex/codexRename/codexInputNotifications/bootCommand/agentEnv/codexIdentity/ptyBinding/claudeParkedJobs/claudeJobs/updater-core/latestTask/transcriptLoader/tabOwnership/ptyTransfer + shared messageCount/tabWorkspace/tabDrag/updateLog + renderer-lib liveness/focusSync/animationSync/theme/navHistory/pins/clipboard/findMatches/messageGroups/codeLang/rowIdentity/mdCopy/mathDelimiters/maxLiveScale/tooltip/bindPolicy/liveOrder/xtermScrollUp/marks/reorder-via-pins/storageSync/tabsPreference/tabPersistPolicy + tabs-and-panes paneModel/tabSelection/dropTarget/ptyHome/ptyStream/ptySnapshot + repo-hygiene lockfileRegistry). The renderer UI is not unit-tested. Two suites are unusual: `codexIdentity` drives the real `execFile` path against stub binaries (the branches deciding whether `lsof` output is trustworthy are what stand between a truncated probe and a *wrong* bind, so they can't be faked), and `ptyBinding` drives a stateful class (`PtyManager`) rather than a pure function, with `node-pty` stubbed via `vi.mock` and the identity resolver injected. Both were built by **mutation-checking**: revert a guard, confirm a named test fails. That found several tests that passed for the wrong reason — do it for any new guard here, or you can't tell a guard from a tautology. `mdCopy` was built the same way and is the strongest argument for the practice: mutation-checking its guards surfaced four real defects the tests had been passing straight over, including an unclamped `slice` that silently dropped a delimiter. **Mutation-check the TEST too, not just the guard.** `tooltip`'s surrogate-pair test was written against a budget whose head and tail both came out even, so a UTF-16 implementation never split a pair and the test passed against a deliberately broken one — it asserted nothing. A test whose fixture can only exercise the happy path is a tautology in the same way a missing assertion is; the fix was choosing a budget with odd parity. **One mutation per line is not enough, either** — `liveOrder`'s stale-row rule was mutated in one direction (which produced a duplicate key and was caught) while a second mutation of the SAME line — keep the dead row's slot and delete the corrected row instead — survived every test, because the fixtures placed the two ids *adjacent*, where both behaviors emit an identical array. Separate the ids in the fixture and assert the full result: two different wrongs must not be able to look the same. **When intercepting and declining are observationally identical, a buffer-observing test proves nothing** — `xtermScrollUp`'s non-top-anchored case stayed green with its guard neutered, because the routine it delegates to branches the same way and produces an identical buffer; only asserting the handler's own return value distinguishes them. **The identical-output trap is the one that keeps recurring** — `dropTarget`'s above-the-strip clamp survived because the fixture listed rows top-first, so a version that measured no distance at all and simply took the first row it enumerated gave the same answer; `tabSelection`'s cross-pane anchor survived because the fixture's two panes held disjoint ids, so a leaked anchor was never *found* and both behaviours fell into the same branch. Before trusting a passing test, ask what the wrong implementation would return **for this fixture** — if it is the same value, the fixture is the bug. Two more of the same shape: `ptySnapshot`'s saved-cursor case passed against a handoff that replayed **nothing at all**, because an empty terminal also lands the follow-up write at column 0 — so it had to assert the restored CONTENT first, before blaming the cursor, or "lost the saved cursor" and "lost everything" were the same observation; and `tabsPreference`'s "absence follows the default" could not be expressed at all while the default was `false`, since a function ignoring the default and hardcoding `false` agrees on every input — the fallback became a **parameter** purely so the rule can be asserted at a default of `true`, which is the only place the two differ. When a rule is about a CONSTANT, a test that compares against that same constant proves nothing; vary it. **A surviving mutant is not always a missing test.** Three guards here were unobservable and were DELETED rather than covered: `pruneEmptyPanes`'s short-circuit, `ptyHome`'s equality check, and `dropTarget`'s empty-array early return all produced exactly what the general path already produced. A guard that cannot be observed reads as load-bearing and is not. And when two pieces of state must agree, prefer making that **structural** over testing it: `ptyStream` kept a chunk list and its byte count in parallel maps, which could diverge invisibly, and folding them into one record made the mutation inexpressible instead of merely caught.
5. `npm run package` — `electron-vite build` + `electron-builder --dir`, rebuilding the installed `dist/mac-arm64/Switchboard.app`. `npm run build` alone does NOT do this. Quit (⌘Q) and reopen the app to load it.

For iterating, `npm run dev` (hot reload) is the inner loop (first run / after an Electron bump: `npm run rebuild` first — node-pty must match Electron's ABI; see `docs/gotchas.md`). The renderer (visual feel, live terminal, drag/scroll) can only be truly verified by a human running `npm run dev` or the freshly-packaged `.app` — typecheck/build/smoke don't catch React-runtime or visual issues. Say so rather than claiming the UI works.

Set `SWITCHBOARD_DEV_LABEL=<name>` before `npm run dev` to tag the window title **and** the title bar (a mono pill left of the gear) — so several dev instances can run side by side and stay tellable apart (there's no single-instance lock; Vite auto-increments the port). Unset in normal and packaged runs, where the title stays a plain "Switchboard".

Set `SWITCHBOARD_FAKE_PARKED=1` before `npm run dev` to give every new Claude terminal a background
agent, so the *work-is-in-a-background-agent* row can be looked at — it otherwise needs a session that
launches an agent and then writes no transcript of its own, which can't be produced on demand. Pairs
with `SWITCHBOARD_FAKE_UNBOUND=1`, which makes every Codex identity probe prove nothing so the
fail-closed unlinked row is reachable. Both inert unless explicitly set.

Set `SWITCHBOARD_FAKE_UPDATE=current|behind|unknown` before `npm run dev` to force the Preferences → Application → Updates check result, so its states are eyeball-able in dev (the real `git ls-remote` check needs a packaged build whose commit is pushed to `main`). Set `SWITCHBOARD_FAKE_UPDATING=1` to hold the Updates setting in its in-flight run state, including the animated `Updating` dots. Inert in production unless explicitly set.

## Conventions

- **Two agents, like two themes.** Switchboard supports BOTH **Claude Code and Codex**; every change must work for — and be considered for — both, the same bar as light/dark. Anything agent-specific branches on `ConversationMeta.agent`; the seam is the main-process agent split (`sessions/{parser,codexParser,codexThreadsDb,codexSessionIndex,rename,codexRename}`, dual-root `indexer`/`watcher`, per-agent `pty/manager` boot). See the two-agent invariant in [docs/design.md](docs/design.md) and the **Multi-agent (Codex)** section in [docs/architecture.md](docs/architecture.md).
- TypeScript strict; 2-space indent; no semicolons (match `src/shared/types.ts`). Prefer named exports. No formatter is configured.
- Main/preload imports are relative; the renderer uses the `@shared` / `@renderer` aliases.
- **Testing:** unit tests live in `test/` (vitest) and cover **pure logic** — main-process parsing/indexing plus renderer-lib helpers pulled out of components (`liveness`, `focusSync`, `animationSync`, `theme`, `navHistory`, `pins`/`reorderArray`, `clipboard`, `findMatches`, `messageGroups`, `codeLang`, `rowIdentity`, `mdCopy`, `mathDelimiters`, `maxLiveScale`, `tooltip`, `bindPolicy`, `liveOrder`, `xtermScrollUp`, `marks`, `reorder`, `storageSync`, `tabsPreference`, `tabPersistPolicy`, and the tabs-and-panes set — `paneModel`, `tabSelection`, `dropTarget`, `ptyHome`, `ptyStream`, `ptySnapshot`); the **renderer UI is not unit-tested**. `bindPolicy` is the pattern to copy when a React effect holds a *decision* rather than a value: the `pty:bound` handler's choice of which session-keyed state migrates is what separates an identity correction from durable data loss, and inside the effect no test could reach it. Two deliberate exceptions drive real machinery instead: `ptyBinding` runs `PtyManager` itself (`node-pty` stubbed, the identity resolver injected) because the probe's retry budget, coalescing, and staleness re-checks exist only as state; and `codexIdentity` runs the real `execFile` path against stub binaries, because the branches deciding whether `lsof` output is trustworthy are what stand between a truncated probe and a *wrong* bind, and a fake can't exit nonzero or get killed mid-write. Reach for either shape only when the behavior genuinely lives in the statefulness or the subprocess. A third departure, `lockfileRegistry`, imports nothing from `src/` at all — it asserts **repo hygiene**, reading `package-lock.json` to prove every dependency resolves from a public host (an allowlist, so an unanticipated host is caught too). npm records the host it actually fetched each package from, which makes the lockfile the one file where a non-public registry can appear without any source change — and `npm ci` then fails for every contributor who cannot reach that host. Add suites of that shape sparingly — the bar is a repo-level invariant no unit test can express. `xtermScrollUp` departs a fourth way: it drives a real *third-party* engine (`@xterm/headless` — the shipped `@xterm/xterm` with the browser renderer removed, so it loads under the node tsconfig), because what it corrects is a disagreement between two of xterm's OWN scroll routines, and a stub would only restate the assumption under test. It therefore also asserts **version lockstep**: `@xterm/headless` must resolve to the same version as `@xterm/xterm`, or the suite validates an engine the app does not ship — bump the two together. Keep pure logic in `lib/` so it's importable under the **node** tsconfig (no DOM lib) — a test-imported module must not touch `window`/`document`, and note that `localStorage` alone slips past because `@types/node` declares it, so a module can look compliant until the first `window` reference breaks a suite that never used it (why `reorder.ts` holds `reorderArray` rather than `usePins`) — nor `electron` (why `theme.ts` is pure with the DOM half in `themeDom.ts`, `updater-core.ts` holds `updater.ts`'s electron-free helpers, and `focusSync.ts` / `animationSync.ts` hold event-ordering rules that their React hooks only bind to browser APIs; see Theming and Renderer state in `docs/architecture.md`). When a signal's correctness lives in an **ordering** rather than a value, extract the ordering — left inside a hook it is the one part no test can reach, and a silent revert to the broken order looks identical to working code.
- Repo-wide test/build is cheap here; to iterate on one suite use `npx vitest run test/<name>.test.ts` or `npm run test:watch`.
